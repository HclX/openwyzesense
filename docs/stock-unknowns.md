# Stock behaviour still to find out

What the stock Wyze Sense devices (sensors and dongle) do that we do not know yet, and that our firmware needs to
match (R1) or would like to. One item per row, with why it matters and how it could be found. Answers go into
`docs/FACTS.md` with their evidence, then the row here is marked done (or removed) in the same commit.

For the full reconstructed C source code of the stock v1 sensors (`contact_v1`, `motion_v1`) and USB dongle
(`gateway_v1.8`) — mapped to TI's SimpleLink CC13x0 SDK (`ti154stack`) with flash and SRAM addresses on every function
and global structure — see [`docs/stock-re/`](stock-re/README.md).

## How to work on an item

**Evidence, not memory.** What counts is a capture or a dump in `ground_truth/` (CLAUDE.md, "What to trust"). Add a
new session folder (`ground_truth/rf/<date>_<time>_...` or `ground_truth/host/<date>_...`), list it in
`ground_truth/README.md` with what was done (which sensor, which press, how long, the time), update
`ground_truth/SHA256SUMS`, and write the FACTS row with status **verified** (or **hypothesis** if one observation
leaves room). Note the exact time of each physical action (a phone stopwatch is fine): most questions are about what
happens after a press.

**Safety rules (the user's house runs these sensors):**
- Receiving is always fine: the SDR, the bridge's read-only API (`GET /api/dongles`, SSE `/api/events`;
  its URL stays out of the repository).
- Never transmit on the house network (PAN 0x845B) without the user's explicit OK (the firmware no longer refuses it,
  #70), never POST to the bridge (scan, pair, raw commands) without the
  user's OK. Transmitting on the test network (PAN 0x65FE) needs the user's OK too.
- Pressing a house sensor's button for long enough makes it leave the house network and try to pair: ask the user
  before doing that to a house sensor.
- No SDR recordings overnight.
- Dumping a stock device: back up its whole flash, CCFG included, first; never erase page 31.

## Done

| # | Answer (with evidence in `ground_truth/firmware/` and [`docs/stock-re/`](stock-re/README.md)) |
|---|---|
| B1 | **Short button press (`< 2.04 s`) on v1 sensors**: `Ssf_buttonClockCb()` (`contact_v1` `0x0d218`, `motion_v1` `0x0d100`) debounces for `40 ms` (`4 × 10 ms`) and counts 10 ms ticks while held low. Releasing below `200` ticks (`< 2.04 s` total) sets `buttonAction = 4` (`Sensor_handleKeys` at `0x0db2c` / `0x0da64`): on `contact_v1` it is a **complete no-op** (no RF packet, no LED blink); on `motion_v1` it arms a one-shot PIR LED test flag (`pirLedTestArm = 1`) so the next motion trigger blinks the LED once (`300 ms`), without sending any button packet. Releasing between `2.04 s` and `3.04 s` (`200..300` ticks) is ignored (`buttonAction = 0`). |
| B2 | **Button hold threshold for pairing vs. stuck-button timeout on v1 sensors**: There is a single hold threshold at **`3.04 s`** (`40 ms` debounce + `300 × 10 ms` ticks). At **exactly `3.04 s` while still held**, `Ssf_buttonClockCb()` checks if the sensor is factory-provisioned (`nv8KeyValidFlag == 1 && nv10FacTestFlag == 1 && nv11LowBatLatch == 0` and `!lowBatBootFlag`): if valid, it immediately blinks the LED **3 times (`400 ms` half-period)**; if unprovisioned (e.g. Zero-MAC) or low battery, it blinks **5 times (`200 ms` half-period)**. Releasing between **`3.05 s` and `8.04 s`** (`301..800` ticks) triggers `Ssf_factoryResetNv()` + join (`buttonAction = 1`). Holding past **`8.04 s`** (`> 800` ticks) cancels the press (`buttonAction = 5`) as stuck-button protection. |
| B3 | **Button press while already joined (v1 sensors)**: Short press (`< 2.04 s`) does nothing on `contact_v1` and arms the one-shot PIR test blink on `motion_v1`. Long press (`3.05 s .. 8.04 s`) **unconditionally wipes all network NV items** (`Ssf_factoryResetNv` at `0x104c4` / `0x10790`: deletes NV items `9, 2, 3, 4, 5, 6`), resets `panId = 0xFFFF`, `shortAddr = 0xFFFF`, `channel = 0xFF` without sending any leave frame to the old dongle, sets `joinCyclesRemaining = 30`, and starts a fresh join scan. |
| B4 | **Complete v1 sensor LED blink table (`Ssf_ledBlink` at `0x0fee4` / `0x101d4`)**:<br>- Normal boot (`V > 2.59 V`): **`250 ms` × 1 blink**<br>- Low-battery boot (`V <= 2.59 V`): **`200 ms` × 5 blinks**<br>- Button held `3.04 s` (provisioned & battery OK): **`400 ms` × 3 blinks**<br>- Button held `3.04 s` (unprovisioned / Zero-MAC / low bat): **`200 ms` × 5 blinks**<br>- Join succeeded (`0xA6` with `status == 0x04`): **`400 ms` × 3 blinks**<br>- Join failed (all 30 scan cycles exhausted): **`100 ms` × 3 fast blinks**<br>- Normal reed switch open/close (`contact_v1`, joined): **0 blinks** (never blinks when joined)<br>- Normal PIR trigger (`motion_v1`, joined): **`300 ms` × 1 blink** only on the *first* motion event after join or short button press (`pirLedTestArm`). |
| B5 | **`motion_v1` GPIO pin map (`0x156b0`) and join scan exit (`0x0da64`)**: On `motion_v1`, `DIO12` is the LED output (active high), `DIO13` is the pairing button (active low), `DIO9` is the primary PIR motion input, and `DIO10` is the factory-test (`W`) input. During pairing, `joinCyclesRemaining` starts at **`30`** full 25-channel scan cycles (waiting `1.0 s` between cycles) before giving up with 3 fast blinks (`100 ms`). |
| R1 | **`motion_v1` `0xA2` active/clear vs. `0xAB` summary**: On rising edge of `DIO9` (`PIR`), `motion_v1` increments `seq_num`, sends **`0xA2` with `state = 1`**, starts a **10-second (`10,000 ms`) window clock** (`0x12578`), and starts a **120-second (`120,000 ms`) motion-clear clock** (`0x125ac`). Across twelve 10-second windows (`12 × 10 s = 120 s`), it counts PIR pulses per 10-second bucket in `pirBuckets[12]` (`0x20001728 + 0x88`). At the end of the 12th window (`event 0x0008`), `Sensor_sendPirSummary_AB()` (`0x0cedc`) sends **`0xAB`**: `[0]=0xAB, [1..8]=MAC, [9]=0x02, [10..21]=pirBuckets[12], [22]=0x01`. When the 120-second clear clock expires without further motion (`event 0x2000`), it increments `seq_num` and sends **`0xA2` with `state = 0`**. Both `contact_v1` (`0x08280`) and `motion_v1` (`0x07fa8`) also send **`0xAD`** (`[0]=0xAD, [1..8]=MAC, [9]=type, [10..21]=12B log entry`) to drain events recorded while offline. |
| R3 | **`contact_v1` and `motion_v1` `0xA1` heartbeat interval**: Both `contact_v1` (`0x12794` -> `0x12440`) and `motion_v1` (`0x12ae8` -> `0x12708`) run a **`300,000 ms` (5-minute)** TI-RTOS clock that increments a software counter up to **`48` (`0x30`)**, sending `0xA1` every **4 hours (`14,400 s`)**. |
| R4 | **`0xA1` data byte (`pt[14]`) on v1 sensors**: Before calling `Sensor_sendHeartbeat_A1()` (`0x0c2f8` / `0x0be78`), `contact_v1` reads live `PIN_getInputValue(DIO7)` (`0` = closed, `1` = open) and `motion_v1` reads `PIN_getInputValue(DIO9) | PIN_getInputValue(DIO10)`, placing the live GPIO state into `pt[14]`. `Sensor_sendHeartbeat_A1()` does not increment `seq_num`. |
| R5 | **Battery byte (`pt[11]`), low-battery flag (`pt[12]`), and sampling time**: `pt[11]` is `AONBatMonBatteryVoltageGet() >> 3` (`V * 32`, i.e. `1/32 V` units). It is sampled at boot (`Ssf_checkBootBattery` at `0x11bc0` / `0x11e3c`: 6 samples at `200 ms` intervals, threshold `<= 0x53` = `2.59375 V`) and **immediately after every radio transmission** (`Ssf_sampleBatteryPostTx` at `0x11c14` / `0x11e90`) to measure voltage under TX load. If post-TX `bat_v32 < 0x54` (`2.625 V`) on **3 consecutive transmissions**, the sensor latches `nv11LowBatLatch = 1` in NV item `(6, 11, 0)` and sends `pt[12] = 0x01` (instead of `0x00`) in subsequent `0xA1`/`0xA2` reports. |
| R6 | **Temperature byte (`pt[10]`)**: Confirmed in both binaries: calls TI DriverLib `AONBatMonTemperatureGetDegC()` (`contact_v1` `0x12c88`, `motion_v1` `0x12f40`), returning signed integer °C in `pt[10]`. |
| R7 | **Sequence counter persistence (`NV item 4`) and behaviour after join**: On a 3-second button press (`Ssf_factoryResetNv` at `0x104c4` / `0x10790`), NV item `(6, 4, 0)` is deleted and `seq_num` resets to `0`. Across normal reboots (`Ssf_initSeqCounter` at `0x10278` / `0x10558`), the firmware reads 4-byte `savedSeq` from NV item `(6, 4, 0)`, sets `seq_num = savedSeq + 25`, and writes `seq_num` back to NV item `(6, 4, 0)`; at runtime (`0x11cf4` / `0x11f6c`), it only writes to NV item `(6, 4, 0)` every **25 increments**. |
| R8 | **Sensor polling and retry rules after `0xA1`/`0xA2`**: After transmitting `0xA1` or `0xA2`, `contact_v1` polls via 802.15.4 Data Request every **`700 ms` up to `10` times** (`7.0 s` window) and `motion_v1` polls every **`800 ms` up to `5` times** (`4.0 s` window) until `0xB0` arrives. If all polls fail, the event is pushed to the 50-entry offline history ring buffer (later drained via `0xAD`). |
| R10 | **Copies a stock sensor sends of a report nobody ACKs**: the v2 contact sends **6** (1 + 5 retries) over ~2 s, and a new event cuts them short; ACKed, 1. Measured in the roaming hardware check (its owner unplugged, the other gateway overhearing): FACTS.md, `host/2026-11-01_roaming_stock_contact_retries`, `test_stock_retries.py`. Not yet for v1 sensors or other types (static: their MAC retry setting). |
| J1 & J2 | **`0xA3` layout and bytes 11–15 on v1 sensors (`Sensor_sendJoinReq_A3` at `0x0da30` / `0x0d968`)**: `[0]=0xA3`, `[1..8]=MAC`, `[9]=sensor_type` (`0x01` contact / `0x02` motion), `[10]=fw_version` (`0x16` contact / `0x18` motion), `[11]=bootBatV32` (explains why byte 11 varies with supply voltage!), `[12]=nv8KeyValidFlag` (`0x01` if provisioned, `0x00` on Zero-MAC), `[13]=nv10FacTestFlag` (`0x01` if factory test passed), `[14]=resetCauseFlag`, `[15]=0x00`. On the gateway (`0x03512`), `0x5320` only forwards `A3[0..10]` (`11` bytes) to the host and ignores `A3[11..15]`. |
| J3 | **`0xA6` validation on v1 sensors (`Sensor_dataIndCb` at `0x064f8` / `0x05ee8`)**: After decrypting `0xA6` (AES-128-ECB then XXTEA-19), the sensor copies **only `A6[0..10]`** (ignoring `A6[11..15]`), checks `A6[1] == 0xFF`, and checks `A6[2] == 0x04` (join accepted: writes `1` to NV item 9, blinks LED `400 ms × 3`, syncs 64-bit ms clock from `A6[3..10]`) or `A6[2] == 0x05` (decommission: writes `1` to NV item 11). |
| J5 | **`0xA5` XXTEA-19 on sensor and gateway**: `Sensor_sendJoinResp_A5()` (`0x0f270` / `0x0f764`) encrypts the 16-byte `0xA4` token in-place using 19-round big-endian XXTEA (`0x07f98` / `0x0842c`) with the 16-byte per-sensor key from NV item 8. On the gateway (`0x03512..0x03552`), the CC1310 **never verifies `0xA5` itself**: it forwards `A5[0..26]` to the host in `0x5322` and waits for the host to send `0x4321`/`0x5323`. |
| J6 | Stock sensors take our A6 mark: the v2 contact, v1 motion and climate paired with it and reported as usual (FACTS.md §9, 2026-10-24). Confirmed in `contact_v1` (`0x064f8`) and `motion_v1` (`0x05ee8`) binaries: stock sensors only copy `A6[0..10]` and ignore `A6[11..15]`. |
| D1 | **Why no `0xB0` for types `0x0E`/`0x0F`, and `0xB0` byte 9 (`0x28`)**: In `gateway_v1.8` (`0x0e848..0x0e882`), `Collector_handleReport()` explicitly checks `if (sensorType != 0x0E && sensorType != 0x0F)` before calling `Cllc_sendTimeSync_B0()` (`0x0e88c`). Inside `Cllc_sendTimeSync_B0()` (`0x0e8fa`), `b0[9] = 0x28` is a hardcoded literal constant (`movs r3, #0x28`), and stock sensors (`0x064f8` / `0x05ee8`) only read `b0[1..8]` and ignore `b0[9]`. |
| D2 & D3 | **Host packets `0x535E`, `0x5335`, `0x5355`, `0x5337`, `0x433F`/`0x5340`, and `0x4370` in `gateway_v1.8`**:<br>- **`0x535E`**: Sent in 3 error paths: (1) UART RX checksum error (`0x0730a`, 0B payload), (2) 802.15.4 indirect TX failure (`0x0d35e`, 1B payload = `ApiMac_status_t`, e.g. `0xF1` `transactionOverflow`), and (3) duplicate `0xB4` sequence number (`0x0401a`, 2B seq payload).<br>- **`0x5335`**: Triggered by host `0x4334 <count>` (`0x03218`); `Collector_process()` (`0x01fd4`) sends up to 30-byte chunks from internal diagnostic log buffer `0x20001867`.<br>- **`0x5355`**: Sent by `Collector_dataIndCb()` (`0x04166`) when RF opcode `0xEA` arrives (the dispatch at `0x03fd4`; an earlier reading said `0xE8`, FACTS §4.0) (`pkt[0..pkt[10]+10]` + `-rssi`).<br>- **`0x5337`**: Drains the 30-entry × 22-byte circular buffer (`0x20001d1c`) of `0xA2` events received while the host had not ACKed `0x5319` (`0x01d42`, `0x03214`).<br>- **`0x433F` -> `0x5340` / `0x4341`**: In `Uart_processCommands()` (`0x02cec -> 0x03202`), host `0x433F` replies `0x5340`, and host `0x4341` (`0x031fe`) ACKs `0x5340` (confirming `wyzesense2mqtt`'s direction).<br>- **`0x4370`**: Handled at `0x02d06 -> 0x031ba`, replying with `0x53EA` (0-byte payload). |
| D6 | **What a stock dongle answers to our `0x53F0` (feature flags)**: In `Uart_processCommands()` (`0x02bc0..0x02d38`), command byte `0xF0` hits the default branch (`0x032dc`), so a stock dongle **ignores `0x53F0` completely** (sends only the low-level async ACK `0x53FF` if sent as `0x53`, and no `0x53F1` reply). |
| D7 | **NV item 5 trailing 12 bytes and NV item 1 layout (`gateway_v1.8` `0x0e56c`, `0x13358`)**: Because the dongle uses TI's `ti154stack` Collector (`csf.c`), NV item `(6, 5, sub)` is literally TI's 24-byte `Llc_deviceListItem_t` (`{ ApiMac_deviceDescriptor_t devInfo; ApiMac_capabilityInfo_t capInfo; uint16_t msa; }`). In the trailing 12 bytes (`00 00 00 00 00 01 00 00 00 00 00 00`), byte 17 (`0x01`) is `capInfo.allocAddr = true` (from the sensor's 802.15.4 Association Request capability byte `0x80`), bytes 12–16 are the other 5 `false` capability booleans, bytes 18–19 and 22–23 are 4-byte struct alignment padding, and bytes 20–21 are `uint16_t msa = 0`. NV item `(6, 1, 0)` (7 bytes) is packed `Llc_netInfo_t` (`{ isFh, channel, panID, shortAddress, state }`). |
| D8 | **How a stock dongle handles reports from an unknown (unpaired) sensor (`gateway_v1.8` `0x03efc`, `0x035ca`)**: `Collector_dataIndCb()` checks both the in-RAM short-address list (`0x20001994`) before AES decryption and `Csf_findDeviceByMac()` (`0x10460`, searching NV item 5 for the 8-byte ASCII MAC) after AES decryption. If the MAC is not in NV item 5 (`returns -1`), the stock dongle **silently drops the packet** (no `0xB0` sent on air, no `0x5319` sent to host). |
| Z1 | **Root cause of the v1 Zero-MAC bug (`contact_v1` `0x07c18`, `0x11c50`, `0x0cd1c`)**:<br>1. CCFG `0x0001FFCC` is **write-only** in stock sensor firmware: it is only referenced in `FactoryTest_processUartCmd()` (`0x0cd1c` / `0x0cc14`) command `0x08`, which writes the MAC to both `0x0001FFCC` and NVOCTP item `(6, 8, 0)`.<br>2. At boot, `Ssf_readMacAndKey()` (`0x11c50` / `0x11ec8`) **only reads NVOCTP item `(6, 8, 0)`** and never falls back to `0x0001FFCC`. If NV item 8 is missing, the RAM MAC buffer (`0x20000aac` / `0x20000f08`) stays `00 00 00 00 00 00 00 00`.<br>3. In `Sensor_init()` (`0x07c18` / `0x080ac`), **before** checking battery voltage (`<= 0x53` = `2.59 V`), the firmware unconditionally increments and writes NV item `(6, 6, 0)` (`bootCounter`, `0x1216c`) and NV item `(6, 4, 0)` (`seqNum + 25`, `0x10278`) on **every boot**. During a slow coin-cell death, repeated brownout resets fill NVOCTP page 30 (`0x1E000`) until `NVOCTP_compactPage()` triggers a flash sector erase; the erase current spike causes an immediate brownout mid-erase, wiping page 30 (and NV item 8) while leaving CCFG `0x0001FFCC` intact. Restoring NV item `(6, 8, 0)` in page 30 (or sending factory UART command `0x08`/`0x0A` with `W` held low at boot) recovers the stock firmware without touching code pages. |
| Z2 | **`contact_v1` pins and `W` pad (`0x152cc`, `0x0c8e0`)**: In `contact_v1`, `DIO10` (`W` pad) is sampled at boot by `FactoryTest_taskFxn()` (`0x0c8e0`). When `DIO10` is held low at reset, the stock firmware enters Factory Test mode on `UART0` (`DIO1` RX / `DIO0` TX at 115200 baud) and accepts provisioning commands `0x02..0x18`. |
